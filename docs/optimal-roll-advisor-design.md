# OptimalRoll Advisor — Design and Implementation Plan

## 1. Purpose

This document describes the behavior, architecture, and implementation plan for
the OptimalRoll Advisor. It expands on the general roadmap in
[optimal-roll-implementation-roadmap.md](optimal-roll-implementation-roadmap.md)
and focuses on the strategy layer and its presentation in the application.

The Advisor should answer two questions:

1. Before the rolling phase ends, which dice should the player keep and which
   dice should they reroll?
2. After rolling ends, or when stopping early is preferable, which scorecard
   field and column should receive the result?

A recommendation must account for both the current dice and the complete
scorecard state. A figure with no remaining legal field must not increase the
value of a decision. Likewise, the Advisor must not suggest a figure in a
closed column or a school field that has already been used.

The first implementation does not require machine learning. With six dice, the
decision space is small enough to calculate optimal decisions within a turn
using exact probabilities.

## 2. Scope of the First Version

The first complete Advisor should:

- work with either one or two rolls remaining,
- consider ending a turn before all three rolls have been used,
- analyze every possible set of kept dice,
- consider every legal school field and figure,
- distinguish identical fields in different columns,
- never suggest occupied fields,
- respect whether each figure column is open,
- treat Chance as a normal field that can only be consumed once per column,
- include a pijol as an emergency way to finish a turn,
- return the best recommendation and several useful alternatives,
- provide a human-readable explanation,
- remain independent of Flutter and the user interface,
- be deterministic and thoroughly testable.

The first version does not need to solve the entire game with mathematical
optimality. It should solve the current turn exactly while estimating the
long-term effect of scorecard changes with explicit heuristics.

## 3. Core Behavior

### 3.1. Recommend a Decision, Not a Single Figure

One keep decision may lead to several valuable outcomes. Consider:

    2, 2, 5, 5, 1, 4

Keeping 2, 2, 5, 5 may eventually produce:

- Three Pairs,
- Two Triples,
- Full House,
- Four Plus Two,
- a useful school result,
- Chance.

The Advisor should not evaluate a decision solely by the probability of
completing one named figure. It should aggregate the value of all possible
outcomes and select the best legal scorecard entry separately for every final
roll.

### 3.2. The Scorecard Is Part of the Input

The same dice can require a completely different decision depending on the
scorecard. If all three Two Pairs fields are occupied, rolling two pairs no
longer has direct value as that figure. The dice may still be useful for other
figures or school entries.

The Advisor input must include:

- all six die values,
- the number of rolls remaining,
- every school field in all three columns,
- every figure field in all three columns,
- all pijols,
- whether each figure column is open,
- optionally, the stage of the game and a risk profile.

### 3.3. A Turn May End Early

After the first or second roll, the player has two kinds of legal action:

1. record the current result,
2. keep any number of dice and roll again.

The Advisor must compare those choices. If recording the current roll has more
value than continuing, the recommendation should be “Score now,” rather than a
reroll made merely because another roll is available.

After the third roll, rerolling is no longer possible. The Advisor must point
to the best legal scorecard entry.

## 4. Required Domain Model Changes

### 4.1. Unambiguous Scoring Options

The current ScoringOption identifies a figure or school face, but does not
identify its column. This is insufficient because recording the same figure in
different columns may have different strategic value.

A scoring option should represent one concrete scorecard field:

    enum ScoringOptionType { school, figure, pijol }

    class ScoringOption {
      final ScoringOptionType type;
      final int columnIndex;
      final int points;
      final int? schoolFace;
      final Figure? figure;
    }

Examples of distinct moves:

    Two Pairs, column 1, 18 points
    Two Pairs, column 3, 18 points
    School 5, column 2, 5 points
    Pijol in General, column 1, 0 points

The legal move generator should return concrete fields instead of figure types
alone. This also allows the UI to highlight the exact recommended cell.

### 4.2. Pijol as a Domain Move

A pijol should be generated by the domain rules rather than existing only as a
widget action. The Advisor needs a legal fallback after the final roll.

The generator should return a pijol option for each empty figure field in which
it is legal. Whether a pijol is allowed only in an open figure column should be
made explicit in the game specification and covered by tests.

### 4.3. Non-Mutating Simulation

Strategy calculations must not mutate the live game state while exploring
possible moves. The domain needs either:

- an immutable GameState with copyWith, or
- a function that copies a state and applies one move to the copy.

For example:

    GameState applyScoringOption(
      GameState state,
      ScoringOption option,
    );

This must be a pure function.

### 4.4. Stable State Keys

Memoization requires a stable representation containing:

- counts of ones through sixes,
- the number of remaining rolls,
- the status and value of every scorecard field,
- any strategic weight configuration that changes the result.

During a single turn, the scorecard does not change until a result is recorded.
Its fingerprint can therefore be calculated once per Advisor request.

## 5. Advisor Output Model

The strategy engine should return structured domain data, not UI strings.

    sealed class AdvisorAction {}

    class RerollAction extends AdvisorAction {
      final List<int> keptDieIndices;
      final List<int> rerolledDieIndices;
    }

    class ScoreAction extends AdvisorAction {
      final ScoringOption option;
    }

    class AdvisorRecommendation {
      final AdvisorAction action;
      final double expectedTurnScore;
      final double strategicValue;
      final List<AdvisorTarget> likelyTargets;
      final List<AdvisorAlternative> alternatives;
      final AdvisorExplanation explanation;
    }

Die indices are required by the UI even if the solver internally uses face
counts. Equal-valued dice are strategically interchangeable, but the interface
still needs to know which visible tiles to select.

The likelyTargets list should describe the most important favorable outcomes
of a keep decision. It must not imply that the solver is pursuing one figure
regardless of all other outcomes.

## 6. Solver for One Remaining Roll

### 6.1. Generating Keep Decisions

Six dice produce 64 keep masks:

    000000 — reroll every die
    111111 — keep every die
    101100 — keep selected dice

A bit indicates whether the die at that position remains unchanged. With
duplicate values, multiple masks may be strategically equivalent. The initial
implementation may evaluate all 64 masks. A later optimization can deduplicate
them by representing the kept dice as face counts:

    [kept ones, kept twos, ..., kept sixes]

### 6.2. Enumerating Outcomes

Rerolling n dice produces 6^n ordered outcomes. The largest case is:

    6^6 = 46,656

For every outcome, the solver should:

1. combine the kept and newly rolled dice,
2. generate every legal scoring option,
3. evaluate every option,
4. choose the best option for that outcome,
5. add its probability-weighted value to the keep decision.

The value of a keep mask is:

    Q(mask) = sum over outcomes(
      probability(outcome)
      × bestScoringValue(outcome, scorecard)
    )

The best action is the mask with the largest Q, unless scoring the current roll
immediately has a greater value.

### 6.3. Aggregating Equivalent Outcomes

Eventually, the solver should generate count distributions rather than ordered
sequences. For example, [1, 2] and [2, 1] produce the same final dice state, but
that state has probability 2 / 36.

The probability of a count distribution is calculated with the multinomial
coefficient:

    P(c1, ..., c6) =
      n! / (c1! × ... × c6!) × (1/6)^n

This substantially reduces the number of unique states, especially when two
rolls remain.

## 7. Solver for Two Remaining Rolls

With two rolls remaining, the first keep decision cannot be evaluated from the
next roll alone. After every possible second roll, the Advisor must choose the
best action again.

The central value function is:

    V(dice, rollsLeft, scorecard) = max(
      bestScoreNow(dice, scorecard),
      max over keep masks(
        expected value of V(
          nextDice,
          rollsLeft - 1,
          scorecard
        )
      )
    )

The terminal condition is:

    V(dice, 0, scorecard) =
      best legal scorecard entry

Results should be memoized using:

    (dice face counts, rollsLeft, scorecard fingerprint)

Because the scorecard stays unchanged during rerolls, the fingerprint can be
shared by the whole calculation.

## 8. Scoring Utility

### 8.1. Why Immediate Points Are Not Enough

Optimizing only the points earned in the current turn creates short-sighted
behavior. Such an Advisor may:

- consume Chance too easily,
- record a mediocre result in a valuable field,
- ignore an opportunity to open a figure column,
- fail to recognize an approaching school bonus,
- use a pijol too readily and lose the +100 perfect-column bonus.

The result should expose two separate measurements:

1. expectedTurnScore — expected real points from the current turn,
2. strategicValue — an evaluation that includes future consequences.

### 8.2. Initial Strategic Heuristic

The first heuristic may use:

    strategicValue =
        points
      + schoolBonusDelta
      + columnOpeningValue
      + perfectColumnBonusDelta
      - fieldOpportunityCost
      - chanceConsumptionCost
      - pijolCost

#### Recorded Points

These are the points written in the field. A school result may be positive,
zero, or negative.

#### School Bonus Change

The utility should include crossing the 10, 20, 30, and later thresholds. For
example, moving the raw school score from 10 to 11 immediately adds a +50
bonus.

A later version may estimate the probability of eventually reaching a bonus,
rather than considering only a bonus triggered immediately.

#### Opening a Column

The third school entry opens the figure section in that column. This materially
changes the player's available moves and deserves additional value, especially
when no other figure column is open.

#### Field Opportunity Cost

Recording a result removes the possibility of using that field later. Initially
this cost can be configured manually for each figure. Later it should be
estimated from simulations as the expected future value of leaving the field
available.

Rarity alone should not define opportunity cost. A rare figure is only valuable
to preserve if it has meaningful expected value in future play.

#### Chance Consumption Cost

Chance is a flexible emergency field. Recording a low Chance early in the game
should usually cost more than recording the same value near the end.

#### Pijol Cost

A pijol should account for:

- zero points in the current field,
- the lost future value of that field,
- loss of the +100 bonus if the column did not already contain a pijol.

### 8.3. Explicit Configuration

Heuristic weights should live in a dedicated configuration object:

    class AdvisorWeights {
      final double openingColumnValue;
      final double chanceCostEarly;
      final double chanceCostLate;
      final double pijolBaseCost;
      final Map<Figure, double> fieldOpportunityCosts;
    }

This makes it possible to:

- test different strategies,
- calibrate values using simulations,
- support conservative, balanced, and aggressive profiles,
- explain why a decision was selected.

Strategic value must not be displayed as guaranteed or expected points. It is
an internal evaluation containing heuristic adjustments.

## 9. Risk and Tie-Breaking

Two actions may have almost equal expected values while carrying very different
risk. In addition to the mean, the solver may calculate:

- probability of a negative score,
- probability of requiring a pijol,
- median result,
- a lower percentile, such as the score reached in at least 80% of outcomes,
- probability of completing important available figures.

The default tie-break order can be:

1. higher strategic value,
2. higher expected real score,
3. lower pijol probability,
4. better lower percentile,
5. fewer rerolled dice,
6. stable mask order for deterministic behavior.

A future player risk profile may modify this ordering.

## 10. Advisor Explanations

The solver should return structured reasons. The UI layer should translate
those reasons into localized text. It should not attempt to reverse-engineer an
explanation from the final numeric score.

Possible reason codes include:

    preservesTwoPairs
    targetsThreePairs
    targetsFullHouse
    opensFigureColumn
    crossesSchoolBonusThreshold
    avoidsOccupiedFigure
    protectsChance
    reducesPijolRisk
    scoreNowDominatesReroll

Example:

    Keep 2, 2, 5, 5. This setup supports several valuable outcomes:
    Three Pairs, Full House, and Four Plus Two. All Two Pairs fields
    are already occupied, so that figure does not contribute to this
    recommendation.

The Advisor should avoid “Best target: X” when a recommendation derives its
value from several different figures.

## 11. Visual Presentation

### 11.1. Placement

The primary Advisor card should appear directly below the dice and above the
list of currently available scoring options. The player sees the recommended
action first, followed by details and alternatives.

### 11.2. Reroll Recommendation

Example layout:

    ┌──────────────────────────────────────────┐
    │ RECOMMENDED MOVE                         │
    │                                          │
    │  [2] [2] [5] [5]   [1] [4]              │
    │       KEEP           REROLL              │
    │                                          │
    │ Keep: 2, 2, 5, 5                        │
    │ Reroll: 1 and 4                          │
    │                                          │
    │ Main opportunities:                      │
    │ • Three Pairs                            │
    │ • Full House                             │
    │ • School 5                               │
    │                                          │
    │ Expected turn score: 18.4 pts            │
    │ Pijol risk: 3%                           │
    │                                          │
    │ [Apply selection]      [Alternatives]     │
    └──────────────────────────────────────────┘

Suggested die styling:

- green border and lock icon — keep,
- orange border or reduced emphasis — reroll,
- neutral appearance — no recommendation has been calculated yet.

“Apply selection” should update heldDice, but should not roll automatically.
The player remains in control and may alter the selection manually.

### 11.3. Recommendation to End the Turn

If the current score is better than continuing:

    ┌──────────────────────────────────────────┐
    │ SCORE NOW                                │
    │                                          │
    │ Two Pairs — 18 points                    │
    │ Column 2                                 │
    │                                          │
    │ Rolling again has an expected value      │
    │ 4.2 points lower.                        │
    │                                          │
    │ [Show field in scorecard]                │
    └──────────────────────────────────────────┘

Selecting the recommendation may scroll to or highlight the exact field. The
entry should still require confirmation.

### 11.4. View After the Third Roll

After the third roll, the card should show scoring actions only:

    Best entry
    Two Pairs — column 2 — 18 pts

    Alternatives
    1. School 5 — column 1 — 5 pts
    2. Chance — column 3 — 21 pts
    3. Pijol: General — column 1 — 0 pts

Strategic order does not have to match raw-point order. Chance for 21 points may
rank below a proper figure worth 18 if preserving Chance has significant future
value.

### 11.5. Alternatives

The default UI should show no more than three alternatives:

    1. Keep 2, 2, 5, 5 — value 18.4
    2. Keep 5, 5 — value 17.8
    3. Keep 2, 2 — value 16.9

Rather than displaying an artificial confidence percentage, the UI should show
the value gap between the first and second action. A small gap communicates
that both choices are nearly equivalent.

### 11.6. Calculation State

With one roll remaining, a result should appear almost immediately. With two
rolls remaining, the UI may briefly show:

    Analyzing possible rolls…

The calculation must not block animations. If profiling shows noticeable work,
it should run in an isolate. An outdated request must be cancelled or ignored
when the dice or scorecard changes.

## 12. Integration with the Turn Flow

The Advisor should recalculate after:

- the first roll,
- the second roll,
- a manual change to held dice, if the UI displays the value of the player's
  selection,
- a scorecard change,
- restarting the game.

No recommendation is needed before the first roll. After recording a result,
the recommendation from the previous turn must be cleared. A new recommendation
appears after the next “First roll.”

The number of rolls remaining should be derived consistently:

    rollsLeft = 3 - rollsUsed

After the first roll, rollsLeft is 2; after the second, it is 1; after the
third, it is 0.

## 14. Proposed API

    class AdvisorInput {
      final DiceRoll dice;
      final GameState gameState;
      final int rollsLeft;
      final AdvisorWeights weights;
    }

    abstract interface class GameAdvisor {
      AdvisorRecommendation recommend(AdvisorInput input);
    }

The application-facing API may be asynchronous when calculations are expensive:

    Future<AdvisorRecommendation> recommendMove(
      AdvisorInput input,
    );

The solver itself should remain synchronous and pure. Running it in an isolate
is an application-layer responsibility.

## 15. Testing Strategy

### 15.1. Outcome Generator Tests

Verify:

- the number of outcomes when rerolling zero through six dice,
- probabilities sum to 1,
- aggregated count probabilities are correct,
- kept dice never change.

### 15.2. Legal Scoring Tests

Required cases:

- an occupied figure is not returned,
- a figure occupied in all three columns contributes no Advisor value,
- a figure is available only in an open column,
- the same figure available in two columns creates two separate options,
- an occupied school field is not returned,
- a pijol identifies a concrete column and figure,
- every valid non-finished game state has a legal way to end the turn.

### 15.3. Keep Decision Tests

Useful cases with clear expected behavior include:

- six equal dice should recommend scoring Marshal when a field is available,
- a completed high-value figure should beat an unjustified risky reroll,
- with five equal dice and Marshal available, rerolling the sixth die should be
  considered against scoring General immediately,
- 1,2,3,4,5,x should correctly value Small, Big, and Great Straight depending
  on available fields,
- an unavailable figure must never contribute points to a keep decision,
- changing only the scorecard can change the recommended keep mask,
- when rollsLeft is zero, the action is always scoring and never rerolling.

### 15.4. Strategic Utility Tests

Test each heuristic component separately:

- crossing a school bonus threshold,
- opening a column with the third school entry,
- consuming Chance early versus late,
- placing the first pijol in a column,
- placing another pijol in a column that already lost its bonus,
- opportunity cost for each figure field.

### 15.5. Regression Tests

Every discovered strategy defect should receive a minimal test containing the
complete dice and scorecard state. Recommendations must be deterministic and
must not depend on map iteration order or randomness.

## 16. Performance

The initial implementation should be profiled before adding complicated
optimizations. Natural optimizations include:

- face counts instead of treating die order as strategic state,
- removing equivalent keep masks,
- aggregating outcomes by count distributions,
- memoizing values by dice counts and rolls remaining,
- calculating the scorecard fingerprint once,
- caching terminal evaluations,
- cancelling or ignoring stale calculations after input changes.

Full enumeration with one remaining roll is small. Two rolls require
memoization, but remain practical for six dice. Performance must be measured on
target mobile devices rather than inferred only from desktop development.

## 17. Strategy Validation

Once the Advisor works, a full-game simulator should compare:

- random keep decisions,
- a simple single-figure target strategy,
- current-turn point maximization,
- the Advisor with strategic heuristics,
- different weight sets and risk profiles.

Core metrics should include:

- average final score,
- median final score,
- lower and upper percentiles,
- average number of pijols,
- school bonus frequency,
- perfect-column bonus frequency,
- usage frequency of each figure,
- recommendation calculation time.

The simulator is more important than introducing a neural network early. It
provides an objective way to verify whether a heuristic change improves play.

## 18. Implementation Stages

### Stage A — Prepare the Domain

1. Add the column index and action type to ScoringOption.
2. Generate pijols as legal domain moves.
3. Add pure copying and move application for GameState.
4. Expand legal move tests.

Completion criterion: every possible scoring action has an unambiguous model
and can be simulated without modifying application state.

### Stage B — Evaluate a Final Roll

1. Implement ScoringUtility.
2. Select the best entry by real points.
3. Add strategic components through configurable weights.
4. Return a ranked list of legal entries.

Completion criterion: for any roll with no rolls remaining, the Advisor
identifies one concrete field and sensible alternatives.

### Stage C — One Remaining Roll

1. Generate unique keep decisions.
2. Generate every possible reroll outcome.
3. Calculate the expected value of each decision.
4. Compare rerolling with scoring immediately.
5. Return the best action, alternatives, and outcome statistics.

Completion criterion: the result is exact, deterministic, and covered by tests
with manually verified probabilities.

### Stage D — Two Remaining Rolls

1. Add the recursive value function.
2. Add memoization by dice face counts.
3. Measure execution time and memory use.
4. Move calculations to an isolate if necessary.

Completion criterion: the Advisor accounts for selecting dice again after the
second roll and responds smoothly on a target device.

### Stage E — User Interface

1. Add AdvisorCard beneath the main dice.
2. Highlight dice to keep and reroll.
3. Add an “Apply selection” button.
4. Highlight the recommended scorecard field.
5. Display up to three alternatives.
6. Add a short explanation and risk metrics.
7. Handle loading, unavailable recommendations, and stale calculations.

Completion criterion: a player can understand and apply a recommendation
without understanding the underlying algorithm.

### Stage F — Simulation and Calibration

1. Create a complete game simulator.
2. Run thousands of games for different weight sets.
3. Compare strategies using identical random sequences.
4. Tune school, column-opening, Chance, field, and pijol values.
5. Preserve named and versioned weight profiles.

Completion criterion: the Advisor achieves a measurably better final score than
the baseline strategies.

## 19. Future Extensions

Potential later improvements include:

- conservative, balanced, and aggressive profiles,
- opponent-aware recommendations,
- Monte Carlo Tree Search for longer-term planning,
- a value function trained on simulated games,
- player-specific strategy preferences,
- an educational view showing probability calculations,
- evaluation of a manually selected keep decision,
- recommendation history and post-game analysis.

Any learned value function should improve long-term state evaluation, not
replace the deterministic rules engine. Legal moves, scoring, and current-turn
probabilities must remain exact and explainable.

## 20. MVP Completion Criteria

The Advisor MVP is complete when:

- it recommends which dice to keep with one or two rolls remaining,
- it considers scoring before all rolls are used,
- after the third roll it recommends a concrete scoring field,
- it accounts for all three columns and whether each is open,
- occupied fields never contribute to recommendation value,
- school entries, Chance, and pijols are included,
- expected real score is separated from strategic value,
- it provides useful alternatives and a concise explanation,
- it never mutates the live game state,
- it is covered by domain, probability, strategy, and regression tests,
- it performs smoothly on target devices,
- its quality can be measured through repeatable game simulations.
